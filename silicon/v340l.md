# Radeon PRO V340L — not gfx1030

Date: 2026-08-18. **Later.** Test target mentioned by the operator; not today's vLLM work.

## Identity

Linux amdgpu hardware list groups V340L with Vega 10 (RX Vega / WX Vega / V320 / 8200 / 9100 / SSG MxGPU). That is **GCN5 Vega 10**, LLVM target **gfx900**, not RDNA2 gfx1030 and not Vega 20 gfx906.

Public V340 material: dual Vega 10 on one PCIe 3.0 x16 card, 56 CUs per die (3584 SP), HBM2 (commonly 16 GB/die, 32 GB/card), MxGPU/SR-IOV virtualization SKU. One physical card is **two HIP devices**.

Do not load V620 objects, assume wave32, or assume `V_DOT2_F32_F16` / `V_DOT4_I32_I8`.

## What this breaks vs our kernels

| Assumption on V620 | V340L |
|---|---|
| wave32 WGP | wave64 CU |
| `fdot2` / `sdot4` / `sdot8` | Vega packed FMA / older integer paths; no RDNA2 DOT feature list |
| 128 KB LDS/WGP, 64 KB/WG | 64 KB LDS/CU |
| PCIe 4.0, 512 GB/s GDDR6 | PCIe 3.0, HBM2, two GPUs sharing one x16 |
| Occupancy `amdgpu_waves_per_eu` as used on gfx10 | different VGPR/wave accounting |

gfx1100 W7800 kernels are equally non-portable here. Llaminar's current ROCm backend is **gfx906** (Vega 20). That is the closest existing Vega work, still not a V340L drop-in.

## If we ever bench it

1. Confirm `rocminfo` ISA string (`gfx900` expected) and two devices per card.
2. Do not reuse gfx1030 HIP fatbins.
3. Start from Vega packed-fp16 GEMM / gfx906 notes, then retarget.
4. Dual-die + PCIe 3.0 x16 shared link changes any P2P/activation-A2A budget.
5. ROCm support for Vega 10 in 7.x is not assumed; record the exact stack.

Today: ignore V340L in occupancy, HIP MoE, and vLLM fork work.
