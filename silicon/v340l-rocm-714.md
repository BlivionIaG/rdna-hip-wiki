# V340L on ROCm 7.14 / TheRock — enumerate vs compute

Date: 2026-08-28. **Own host.** Not a ROCm fork. Not a vLLM PR. hippih / extras stay HIP. No tok/s.

Companion: [v340l.md](v340l.md) (ISA + same-host ban). Path lock: extras first; hippih gfx900 TU later, on this host.

Read remotely 2026-08-28. Trees not cloned. If a path moved, it is marked.

## Locked (do not contradict)

| Field | Value |
|---|---|
| SKU | V340L = **dual Vega 10**, PCI **1002:6864**, **8 GB HBM2/die**, LLVM **gfx900** |
| ISA | `v_mad_mix_f32` + `v_pk_fma_f16` only. **No** `fdot2` / `sdot4` / `sdot8` (those start at gfx906). **No** `gfx9-generic` (drops `v_mad_mix`) |
| Official | Instinct MI25 / gfx900 last certified **ROCm 4.5**; marked unsupported in **5.0**. **7.14** matrix still unsupported |
| Kernel | Linux amdgpu + vega10 firmware + amdkfd still in-tree (VEGA10 includes V340L) |
| Host | **Own machine.** Same-box ROCm 7 + gfx900 + V620 = remapped-MMIO trap |
| TheRock | `device-gfx900` re-added **PR #3564** (Mar 2026): **build-passing, not sanity-tested**. Many libs excluded |
| Packaging pattern | [mixa3607/ML-gfx906](https://github.com/mixa3607/ML-gfx906) is the live 7.x Vega 20 cook. Other 7.x cooks exist; named below |

## Verdict (one page)

**7.14 will enumerate. 7.14 will compile HIP for `gfx900`. 7.14 will not compute unless a gfx900 rocBLAS Tensile payload is present.** Official packages will not ship that payload. TheRock nightlies advertise `device-gfx900` but have never sanity-tested it. hipBLASLt / CK / rocWMMA / hipTensor are out. First iron bar is one GEMM, not tok/s.

| Layer | Official 7.14.0 | TheRock nightly `device-gfx900` | mixa3607-style TheRock rebuild `-DTHEROCK_AMDGPU_FAMILIES=gfx900` |
|---|---|---|---|
| amdgpu + vega10 fw + amdkfd | In-tree. Should see 1002:6864 | Same kernel | Same kernel |
| `rocminfo` `gfx900` | Possible (HSA still names gfx900). Unsupported SKU | Intended. **Unverified** | Intended. **Unverified on V340L** |
| `hipcc --offload-arch=gfx900` | LLVM still has `gfx900` | Same | Same |
| rocBLAS GEMM | **No** gfx900 extra in official 7.14 | Should build (not excluded). Payload **unverified** | In-tree `vega10_*.yaml` includes **Device 6864**. Best path |
| hipBLASLt / CK / rocWMMA / hipTensor | N/A | **Excluded** | **Excluded** |
| Sanity tested | No (unsupported) | **No** | No (community gfx906 only) |

## Official 7.14 — what is actually listed

ROCm **7.14.0** compatibility matrix (2026-07-16): Instinct column is MI355/350/325/300/250/210/100 (`gfx950` / `gfx942` / `gfx90a` / `gfx908`). Radeon PRO column has **V620** (`gfx1030`), not V340L. **MI25 / Vega 10 / gfx900 are absent.** That is QA scope, not a kernel delete.

Linux 6.18 amdgpu product table still lists `Radeon (TM) (PRO|WX) Vega / MI25 / V320 / V340L / 8200 / 9100 / SSG MxGPU` under **VEGA10**, GC 9.0.1. Vega 20 (VII / MI50 / MI60) is a different row.

## HIP / CLR / ROCr — will load `gfx900`

| File | What it does |
|---|---|
| `ROCm/clr` `hipamd/src/hip_fatbin.cpp` (`b2b5af73`) | Native CO for `amdgcn-amd-amdhsa--gfx900` is preferred. **Fallback** maps gfx900 → `gfx9-generic` if the native object is missing |
| `ROCm/clr` `hipamd/src/hip_comgr_helper.cpp` | Same map: `{"gfx900", "gfx9-generic"}` |
| `ROCm/clr` `hipamd/src/amd_hsa_elf.hpp` | `EF_AMDGPU_MACH_AMDGCN_GFX900 = 0x02c` |
| `ROCm/rocm-systems` `python/rocm-bootstrap/python/rocm_bootstrap/targets.py` | `GFX900 = GfxTarget(name="gfx900", major=9, minor=0, stepping=0, …)` |
| `ROCm/rocm-systems` `projects/rocr-runtime/…` | rocrtst / blit kernels still take `gfx900` as a target string |

Enumerate + launch of a **native** gfx900 fatbin is the intended path. The generic fallback is the trap.

## LLVM — `gfx900` keeps `mad_mix`; `gfx9-generic` drops it

Read `ROCm/llvm-project` `amd-staging` (not cloned). Files: `llvm/lib/Target/AMDGPU/GCNProcessors.td` (`f2e9e8cf`), `llvm/lib/Target/AMDGPU/AMDGPU.td`.

| Target | Feature set | Mix / DOT |
|---|---|---|
| `gfx900` (`FeatureISAVersion9_0_0`) | consumer-common + **`FeatureMadMixInsts`** | `v_mad_mix_*` |
| `gfx906` (`FeatureISAVersion9_0_6`) | consumer-common + **`FeatureFmaMixInsts`** + **`FeatureDLInsts`** + Dot1/2/7/10 | `v_fma_mix_*` + `v_dot*` |
| `gfx9-generic` (`FeatureISAVersion9_Generic`) | consumer-common + `FeatureRequiresCOV6` only | **Neither** MadMix nor FMAMix nor DL DOT |

`GFX9_GENERIC` `CoveredGPUs` includes GFX900 and GFX906. That is a **lowest-common-ISA** bucket. Compiling `--offload-arch=gfx9-generic` for V340L is wrong even though HIP will *load* that object as a fallback.

Asm page (still current): gfx900 VOP3P extras are only `v_mad_mix_f32` / `v_mad_mixhi_f16` / `v_mad_mixlo_f16`. Packed `v_pk_fma_f16` is core GFX9.

## rocBLAS / Tensile — logic is **not** gone

`ROCm/rocm-libraries` `develop` this pass still ships Vega 10 logic YAML. Example:

`projects/rocblas/library/src/blas3/Tensile/Logic/asm_lite/vega10_Cijk_Ailk_Bjlk_HB.yaml` (`d92d89ac`)

Header: `vega10` / `gfx900` / device list includes **`Device 6864`** (V340L). Same list in `asm_ci/` and `asm_full/vega10/`. Also `HSS_BH` (fp16→fp32) files, `MinimumRequiredVersion: 4.24.0`.

`projects/rocblas/library/src/tensile_host.cpp` still has `LazyLoadingInit::gfx900` (probes `TensileLibrary_lazy_gfx900.dat`).

So: **a TheRock gfx900 build can emit a current-tree Tensile payload.** That is not a 4.5-only leftover, and it is not “logic deleted.”

What *is* gone from **prebuilt** 7.x:

| Payload | Official 7.14 | TheRock `device-gfx900` nightly | mixa3607 7.14 gfx906 image |
|---|---|---|---|
| `lib/rocblas/library/TensileLibrary_lazy_gfx900.dat` + `*gfx900*.{co,hsaco}` | Absent (unsupported SKU) | **Unverified.** Build-passing only | Absent (they build **gfx906**) |
| `TensileLibrary_lazy_gfx906.dat` | Absent from official consumer 7.14 | N/A | **Present** (TheRock gfx906 rebuild) |

Community cooks that needed gfx900 GEMM on a **gfx906** 7.2 image copied the 6.3.4 payload (`TensileLibrary_lazy_gfx900.dat` + `*gfx900*.co`) into `lib/rocblas/library/`. That is a backport of the **binary catalog**, not proof that 7.x YAML is gone. Prefer rebuilding TheRock for `gfx900` from the in-tree YAML. Use the 6.3.4 copy only if the nightly `device-gfx900` kpack is empty on iron.

`shared/tensile/Tensile/Configs/rocblas_hgemm_hip_lite.yaml` comments out the vega10 schedule. That is a **tuning-config** comment, not deletion of `asm_lite/vega10_*.yaml`.

## Minimum viable stack (when cards land)

1. **Linux host, own box.** Inbox amdgpu + vega10 firmware + amdkfd. No V620. No Mac vendor blob.
2. **TheRock gfx900 userspace** — nightly `rocm[libraries,device-gfx900]` **or** mixa3607 recipe with `FAMILIES=gfx900`. Confirm `lib/rocblas/library/` contains `TensileLibrary_lazy_gfx900.dat` + `*gfx900*.co`. If empty: rebuild TheRock for gfx900 (in-tree YAML). 6.3.4 copy is last resort.
3. **`hipcc --offload-arch=gfx900`** hello. Never `gfx9-generic`. Never gfx906 fatbins.
4. **One rocBLAS GEMM** (sgemm or hgemm). That is the compute bar.
5. **llama.cpp**: HIP `gfx900` if GEMM works; **Vulkan RADV** if it does not. hippih gfx900 TU later. extras stays on the V620 host.

## First success on iron (8× V340L)

Not tok/s. In order:

1. `lspci -nn` → **16** functions, `1002:6864`. `LnkSta` Gen3 x16 per card (two dies share it). BAR0 ≈ **8G/die**, not a V620 32G.
2. `rocminfo` → **`gfx900` × 16**.
3. `hipcc --offload-arch=gfx900` hello. Load + launch.
4. ISA dump of that object: **`v_mad_mix_*` / `v_pk_fma_f16`**. **No** `v_dot*`.
5. One rocBLAS GEMM on device 0. `rocblas_*gemm` returns 0; `hipDeviceSynchronize` clean.

Stop there. Dual-die scheduling, 8 GB packing, and hippih come after.

## What we should add / improve

- On first boot: list `lib/rocblas/library/*gfx900*` from whichever TheRock we installed. Record the SHA of `TensileLibrary_lazy_gfx900.dat`. If missing, rebuild — do not invent a new YAML first.
- hippih: gfx900 TU (`mad_mix` / `pk_fma`), wave64, 64 KB LDS. New objects. Not a retarget of extras or gfx906.
- llama.cpp Vulkan as the documented fallback, same host, no ROCm GEMM required.
- Keep a mixa3607-shaped TheRock recipe (`FAMILIES=gfx900`, hipBLASLt/CK/WMMA off). Do not publish gfx906 wheels as gfx900.
- Do **not** open PRs to upstream vLLM.

## Do not

| Don't | Why |
|---|---|
| `--offload-arch=gfx9-generic` | Drops `v_mad_mix` (`FeatureISAVersion9_Generic`) |
| Load gfx906 / gfx1030 / gfx1100 objects | Wrong ISA |
| Seat V340L on the V620 / 88096 ROCm 7 host | Remapped MMIO. Also 16 cards / 10 slots |
| `HSA_OVERRIDE_GFX_VERSION` | Real silicon is already gfx900 |
| hipBLASLt / CK XDL / rocWMMA / AITER | Excluded or MFMA/DOT |
| Official 7.14 + hope | Unsupported SKU, no device extra |
| Mac / Thunderbolt vendor blobs | Linux in-tree amdgpu + vega10 fw only |
| tok/s before the GEMM | First bar is enumerate + hello + ISA + one GEMM |
