## Extras modes (2026-08-23)

GPTQ / AWQ / WNA16 are **pack / zeros / group-size**, not a second GEMM. One HIP: `q_gemm_rdna2` / `moe_q_gemm_rdna2` — nibble unpack + ZP + `fdot2`. FA pin is **closed** (`(N,1)` inert). Fat-M / ConfigA leftover unchanged.

| Mode | What HIP does | gfx1030 |
|---|---|---|
| GPTQ `uint4b8` | `zp=8` or GPTQv1 store `7` + kernel `+1` | Same `dequant_4bit_8_fp16` |
| AWQ (group ZP) | Packed `qzeros` via `load4_zeros`; still `w = scale * (q - zp)` then `fdot2` | Dense Live is **loader**. MoE **Not done**: `moe_q_gemm` still synthesizes GPTQv1 zeros (`zero_offset=1`) |
| compressed-tensors WNA16 | Same if shuffled `[K/8,N]` `uint4b8` | Sequential `[K,N/8]` is **Leave** (repack or do not fire) |
| `gs` 32 / 64 / 128 | Scale refresh assumes `gs ≥ 32` (`k += 32`) | Verify; do not invent which gs dense AWQ shipped |
| `gs` 256 or −1 | Not in this HIP loop | **Not done** |
| Triton GEMV / WMMA / `sdot8` | Wrong pack, no opcode, or W4A4 | **Leave** / **Dead** |

Do not add a W4A16 occupancy child. Do not write a second MoE DOT for AWQ — ship packed zeros into the existing `moe_q_gemm` path.

**The kernel you write must:**

1. **Store weights once**, ExLlama-shuffled, 8 nibbles / `uint32`. Same bits as `int8 [N, K/2]` or `int32 [N, K/8]` (hybrid) **or** `uint32 [K/8, N]` (dense RDNA3 / MoE). Do not mix sequential-N packing (`TritonW4A16`) with shuffled-K packing (`gptq_shuffle` / hybrid) without a load-time repack.
2. **Read a nibble in VGPR**, not from a LUT in LDS. After shuffle: `(qa >> {0,4,8,12}) & 0x000F000F` then OR the fp16 magic `0x64006400`. That *is* the dequant. See §1–§2.
3. **Dequant** `w = scale * (q - zp)` in **VGPR**. Accumulator is **fp32**. `zp = 8` for `uint4b8`; GPTQv1 stores `7` and the kernel adds `+1`. Group size **≥ 32** (the RDNA3 scalar loop only refreshes scales every 32 K).
4. **Inner loop** = `__builtin_amdgcn_fdot2` → `V_DOT2_F32_F16` / `V_DOT2C_F32_F16`. hipcc 7.2 will **not** peephole `__hfma2` into DOT2 (comment in `q_gemm_rdna3.cu`). Issue the builtin.
5. **Drop** every WMMA fragment, every `v_wmma_*`, every `__builtin_amdgcn_fdot2_f32_bf16`, every bf16 activation path. Force `--dtype float16`.
6. **Decode (`M=1,2,4`)**: skinny / wvSplitK-style. Stage **A** in LDS (`K·M·2 ≤ 32 768` fp16 elems = 64 KB). Stream packed B. `THREADS=256` (8 waves), `BLOCK_KN=256`, 4 N-columns/thread, `M_COUNT∈{1,2,4}`. K-split via `gridDim.z`, 64-bit CAS into a pre-zeroed fp16 C. Target **≤ 64 VGPR** (16 waves/SIMD).
7. **Prefill (`M≥32`)**: tiled DOT2, **not** WMMA. Start **BM×BN×BK = 64×64×32**, WG=256, LDS ≤ 16 KB (2 WG/WGP). Step to **128×64×32** before 128×128. Do not copy the gfx1100 16×16 fragment layout.
8. **MoE**: copy `moe_q_gemm_rdna3`’s *control flow* (sorted tokens → expert tile → dequant+DOT2 → packed CAS, `output_topk` fuses `moe_sum`). It never used WMMA. Drop the bf16 branch and the `__gfx1100__` guard. `BLOCK_SIZE_M=1` for decode, `4` for prefill (that is what the Python wrapper does).
9. **Occupancy 0 is a real gfx1030 failure mode** (llama.cpp FA: 256 thr / 203 VGPR → `cudaOccupancyMaxActiveBlocksPerMultiprocessor=0`). Check with `llvm-calc-occupancy -mcpu=gfx1030` **and** a runtime occupancy query before shipping a 256-thread / 200-VGPR tile.

That is the whole job. The rest of this note is the evidence.

## 1. Weight packing

Three on-disk layouts exist in vLLM. They are **not** interchangeable at kernel time.

### 1.1 ExLlama shuffle — what both HIP paths actually eat

`qdq_4_rdna3.cuh` `shuffle_4bit_8` (device; same permutation as host `ops.gptq_shuffle`):

```
in:  q[7] q[6] q[5] q[4] q[3] q[2] q[1] q[0]   (LSB first, sequential GPTQ)
out: q[7] q[5] q[3] q[1] q[6] q[4] q[2] q[0]   (even in low 16, odd in high 16)
```

After shuffle, `q[2k]` sits at bits `[4k : 4k+3]` and `q[2k+1]` at `[16+4k : 16+4k+3]`, so **one mask `0x000F000F`** pulls a matching even/odd pair ready to bitcast to `half2`.

Host-side equivalent, hybrid path (`rdna_hybrid_w4a16.py` `pack_int4_exllama_shuffle`):

```
[N, K] uint4 → [N, K//8] int32
interleave order [0,2,4,6,1,3,5,7]:
  packed = v0 | (v2<<4) | (v4<<8) | (v6<<12)
         | (v1<<16) | (v3<<20) | (v5<<24) | (v7<<28)
```

Unshuffle shifts in the Triton skinny-format kernel: `shift[j] = (j//2)*4 + (j%2)*16` → `[0, 16, 4, 20, 8, 24, 12, 28]`. Same permutation.

### 1.2 int8 `[N, K/2]` vs int32 `[N, K/8]` vs int32 `[K/8, N]`

| Layout | Who | Shape | Packed dim | View trick |
|---|---|---|---|---|
| Hybrid / skinny HIP | `RDNAHybridW4A16LinearKernel` | **int8 `[N, K/2]`** stored; HIP reads bytes; Triton does `.view(torch.int32)` → **int32 `[N, K/8]`** | K | Same allocation, two dtypes. Comment: “no dual weight storage.” |
| Dense RDNA3 HIP + MoE | `RDNA3W4A16LinearKernel`, `moe_gptq_gemm_rdna3` | **uint32 `[K/8, N]`** (MoE: **`[E, K/8, N]`**) | K | `permute_param_layout_(input_dim=0, output_dim=1, packed_dim=0)` then `ops.gptq_shuffle` |
| Portable Triton | `TritonW4A16LinearKernel` | **int32 `[K, N/8]`** | **N** | Sequential shifts `[0,4,…,28]`. **Different packing.** `process_weights_after_loading` unpacks `[N, K/8]` → `[N,K]` → transpose → repack `[K, N/8]`. |

`wvSplitK_int4_g` host check (`skinny_gemms_int4.cu`): `Weight tensor must contain M*K/2 bytes for int4 packing`. It accepts either view as long as the **byte count** is `M·K/2`.

**How the HIP kernel reads a nibble** (dense RDNA3, after shuffle), `dequant_4bit_8_fp16`:

```
q0 = (qa        & 0x000F000F) | 0x64006400   // half2(q0+1024, q1+1024)
q1 = (qa        & 0x00F000F0) | 0x64006400   // half2(q2*16+1024, q3*16+1024)
q2 = ((qa>>8)   & 0x000F000F) | 0x64006400
q3 = ((qa>>8)   & 0x00F000F0) | 0x64006400
```

Zeros (packed 4-bit, **not** shuffled the same way): `load4_zeros` in `q_gemm_rdna3.cu`:

```
qcol  = n / 8
shift = (n & 7) * 4
d     = qzeros_row[qcol] >> shift
zeros[0..3] = d & 0xF, (d>>4)&0xF, (d>>8)&0xF, (d>>12)&0xF
```

`n` is a multiple of 4 (`n = offset_n + t*4`), so four consecutive output columns live in one or two `uint32`s.

### 1.3 Group size, zero-points, `uint4b8`

| Item | Dense RDNA3 HIP | Hybrid / skinny | Triton W4A16 | MoE RDNA3 |
|---|---|---|---|---|
| Group sizes | `group_size > 0` and `K % gs == 0`; **loop assumes `gs ≥ 32`** (`q_gemm_rdna3.cu` comment: refresh at `k += 32`) | **32, 64, 128** (`SUPPORTED_GROUP_SIZES`) | `-1, 32, 64, 128, 256` | `gs` from `K / groups`; same ≥32 assumption |
| Symmetric | `scalar_types.uint4b8` only (`RDNA3W4A16LinearKernel.SUPPORTED_QUANT_TYPES`) | `uint4b8` (bias=8) and `uint4` | same two | synthesizes zeros for `uint4b8` |
| Asymmetric zp | not in `SUPPORTED_QUANT_TYPES` | raw zp `[N, K/G]` in act dtype; `(nibble - zp_raw) * scale` | packed `qzeros [K/G, N/8]` | synthesizes only |
| GPTQv1 `+1` | `zero_offset = use_v2_format ? 0 : 1`; Python stores `bias-1 = 7` | baked into magic `0x64086408` when `HAS_ZERO_POINTS=false` | `ZP_BIAS=8`, `HAS_ZP=False` for `uint4b8` | **hardcoded `zero_offset = 1`** |
| `g_idx` / act-order | yes (`b_q_perm = argsort(g_idx)`); A gathered through LDS | **rejected** (`does not support g_idx`) | **rejected** | none |

GPTQv1 wart is documented in `rdna3_w4a16.py`: “the kernel adds 1 to the stored zero, so we encode `(bias - 1)`.” Same sentence in `compressed_tensors_moe_wna16_rdna3.py` `_synthesize_qzeros`.

compressed-tensors checkpoint (Triton docstring): `weight_packed [N, K/8]`, `weight_scale [N, K/G]`, `weight_zero_point [N/8, K/G]`. AWQ often arrives `(K, N)` with `output_dim=1`; hybrid transposes to `(N, K)` before shuffle.

**gfx1030 keep:** shuffle, both views of the same bytes, `uint4b8` + optional raw zp, `gs ∈ {32,64,128}`. **Do not** invent a third pack. If you want one buffer for a future Triton fallback, store **int8 `[N, K/2]` shuffled** (hybrid) and have the DOT2 kernel consume it as `uint32*`.

## 2. Dequant math

### 2.1 The equation

Everywhere that was opened:

```
w_fp16 = scale * (q_uint4 - zp)
```

- Symmetric `uint4b8`: `zp = 8` (or GPTQv1 stored 7 + kernel `+1`).
- Asymmetric: `zp` per group, either packed nibble or raw fp16.

No kernel in this set dequants in LDS on the **scalar / skinny** path. Dequant is **VGPR bit-trick → `half2` / `float`**, then DOT2. The **WMMA** path is the exception: it dequants a 16×16 B tile **into LDS**, then builds a WMMA B-fragment from LDS (`q_gemm_rdna3_wmma.cu` `b_lds[16][16]`). That LDS staging exists to feed WMMA, not because dequant needs SRAM. **Drop it on gfx1030.**

### 2.2 fp16 bit-trick (keep)

`prep_zero_scale_fp16` + `dequant_4bit_8_fp16` (`qdq_4_rdna3.cuh`):

```
half(-1024 - zero) via bits 0xE400 | zero
z1z16[0] = scale * (-1024 - zero)     // low pairs
z1z16[1] = scale * (-64   - zero)     // high pairs (the *16 path)
y1y16[0] = scale
y1y16[1] = scale / 16
dq = hfma2(q_magic, y, z)             // (q+1024)*scale + scale*(-1024-zero)
```

Why `*16` on the high nibble: `0x00F000F0 | 0x64006400` places the nibble in the fp16 mantissa four bits up. fp16 mantissa is 10 bits, so a 4-bit shift still fits. **bf16 mantissa is 7 bits — this trick overflows.** That is why every bf16 path uses `0x43004300` (= bf16(128)) and a 4-bit *right*-shift per pair (`qdq_4_rdna3.cuh` header comment).

WMMA fp16 uses a **precise** variant in the WMMA TU only (`prep_zero_scale_fp16_precise`): subtract `(1024+zero)` as an integer first (exact in `[1024,2047]`), then multiply by scale. Classic FMA form can lose ~0.025/cell at `scale=0.1` because `fp16(scale)` and `fp16((1024+zero)*scale)` do not cancel. They kept the precise form **out** of `qdq_4_rdna3.cuh` because growing the shared header changed hipcc register decisions and **regressed decode tk/s** even when the new functions were unused (`q_gemm_rdna3_wmma.cu` lines 63–68). Lesson: do not casually add helpers to a header the decode TU includes.

### 2.3 Where the math lives; accum dtype

| Path | Dequant location | Accum | Store |
|---|---|---|---|
| Scalar `gemm_q4_kernel_rdna3` fp16 | VGPR (`half2 dq[4][4]`) | **fp32** via `fdot2` | pack 4 lanes → 64-bit CAS `atomic_add_pk4_f16` into pre-zeroed `half` C |
| Scalar bf16 | VGPR, widen to fp32 | fp32 FMA or `fdot2_f32_bf16` | 64-bit CAS `atomic_add_pk4_bf16` |
| Skinny `wvSplitK_int4_*` fp16 | VGPR, same magic | fp32 `fdot2`, then `* scale` | one lane (`threadIdx.x == THRDS-1`) writes after DPP reduce |
| WMMA | dequant B → **LDS** 16×16, A from global | WMMA **fp32** fragment (8 VGPR/lane wave32) | direct write if `K_SPLIT==1`, else 32-bit packed CAS |
| Triton both | in-registers, `tl.dot(..., out_dtype=tl.float32)` | fp32 | store as act dtype |

gfx11 has **no** `v_global_atomic_pk_add_{f16,bf16}` (`q_gemm_rdna3.cu` header). gfx1030 does not either (those landed gfx940 / gfx1250 per the same comment). Keep the CAS loop.

## 3. Inner loop on gfx1100: DOT2 vs WMMA

### 3.1 Exact opcodes

| Use | Opcode / intrinsic | Where |
|---|---|---|
| fp16 scalar / MoE / skinny | `V_DOT2_F32_F16` (VOP3P) or `V_DOT2C_F32_F16` (VOP2 carry form) via `__builtin_amdgcn_fdot2(half2, half2, float, clamp=false)` | `q_gemm_rdna3.cu` `dot22_8_f`; `moe_q_gemm_rdna3.cu`; `skinny_gemms_int4.cu` `DOT2C` |
| bf16 scalar / skinny | `__builtin_amdgcn_fdot2_f32_bf16` → `v_dot2_f32_bf16` (VOP3P, gfx11 `dot12-insts`) | same files, `#else` of `half` |
| bf16 fallback if no packed FMA | widen `<<16` + `v_fma_f32` | `q_gemm_rdna3.cu` comment: “no `v_pk_fma_bf16` on gfx11” |
| Prefill / fat | `__builtin_amdgcn_wmma_f32_16x16x16_f16_w32` / `_bf16_w32` → `v_wmma_f32_16x16x16_{f16,bf16}` | `q_gemm_rdna3_wmma.cu` `wmma_mma` |
| ISA math of DOT2 | `D.f32 = S0.f16[0]*S1.f16[0] + S0.f16[1]*S1.f16[1] + S2.f32` | RDNA 2 ISA §12.10 opcode **19** `V_DOT2_F32_F16` |

RDNA 2 ISA 70648 “Feature Changes in RDNA2 Devices” lists `V_DOT2_F32_F16 / V_DOT2C_F32_F16` and the integer DOT2/4/8 family. **No bf16 DOT, no WMMA.**

hipcc 7.2 does **not** emit `v_dot2_f32_f16` from `__hfma2 + cast + add`. The file quotes a disassembly: `0 v_dot2_f32_f16` vs `256 v_cvt_f32_f16 + 218 v_add_f32` in the `M_COUNT=8` kernel before they switched to the builtin. **Issue the builtin on gfx1030 too.**

### 3.2 Dispatch (current `gptq_gemm_rdna3`)

From `q_gemm_rdna3.cu` host entry + `q_gemm_rdna3_wmma.cu` launcher comments:

```
if (bf16 && M >= 16) or (fp16 && M >= 64):
    WMMA  (requires N%16==0, K%16==0)
      M >= 128           → 128×64, 8 waves, K=32 or 16 / iter
      64 ≤ M < 128, N≥64 → 64×64, 4 waves, 4 WMMA/wave/K-iter
      M ≥ 64, 32≤N<64    → 64×32, 4 waves
      M ≥ 64, N<32       → 64×16, 4 waves
      32 ≤ M < 64        → 32×16, 2 waves, double-buffered LDS
      M < 32             → 16×16, 1 wave
else:
    scalar
      M==1     → M_COUNT=1
      M≤3      → M_COUNT=2
      M≤7      → M_COUNT=4
      else     → M_COUNT=8   // up to M=15; M≥16 “should” have gone WMMA
```

Hybrid is a **different** split: `M ≤ 5` and `K*M ≤ 32768` → `wvSplitK_int4_g`; else Triton skinny-format.

### 3.3 Why WMMA for fat, DOT2 for skinny

Quoted / derived from the files, not invented:

1. **Tile waste.** WMMA is 16×16×16. At `M=1` you compute 16 rows and throw 15 away. Scalar `M_COUNT=1` does one row.
2. **Dequant vs MMA ratio.** Scalar fp16 “bit-trick dequant beats WMMA below M=64” (`q_gemm_rdna3.cu` header point 4). Each WMMA still needs 16×16 dequants into LDS; at small M that dominates.
3. **CU saturation / K-split.** Scalar: `THREADS_X=256`, `BLOCK_KN_SIZE=256`, `gridDim.z = K/256`, each thread owns 4 N columns, output via atomics. They tried `BLOCK_KN=512`: bf16 +5–10% at large M, **fp16 decode +40% worse** on qkv 4096² (`32 → 45 μs` at M=1) because `16 waves/block × 16 blocks` only filled **~8 of 96 CUs** on a 7900 XTX. Reverted to 256.
4. **WMMA needs K-split to fill the chip** at moderate M: “at `gridDim.z=4`, K=4096, WMMA jumps from 17% to ~67% wave-slot saturation” (`q_gemm_rdna3_wmma.cu`).
5. **Peak.** GPUOpen: RX 6950 XT **256** FP16 FLOPS/clk/CU (packed DOT/FMA); RX 7900 XTX **512** via WMMA. Fat GEMM is the first place the 2× shows up. Skinny is memory-bound; extra FLOPS do not pay for fragment setup.
6. **Separate TUs.** Putting WMMA in the same translation unit as the scalar kernel “silently miscompiled the M=1 path” (hipcc TU-level register / SGPR heuristics). Keep decode and prefill in **two files** even on gfx1030.

### 3.4 WMMA fragment facts you must **not** port

From `q_gemm_rdna3_wmma.cu` + GPUOpen WMMA article (already in the LDS brief):

- Tile **16×16×16 only**. A/B: 16 elems/lane (8 VGPR fp16). C: 8 VGPR wave32, unpacked, fp32.
- Wave32: lanes **0–15 must equal 16–31** on A and B fragments.
- A column-major, B/C/D row-major. C: `lane_lo` = column; lanes 0–15 even M rows, 16–31 odd.
- `~16 cycles` per WMMA on wave32 (file comment).
- No fp16/bf16-accum 16×16×16 they want; always fp32 C.

None of that has an analogue on gfx1030.

## 5. Tile / occupancy on gfx1030

### 5.1 Occupancy budget (wave32)

LLVM `getTotalNumVGPRs=1024`, granule 16, 16 slots/SIMD (companion brief). V620 = **72 CU = 36 WGP** (AMD product page 72 CU; WGP = CU/2).

| VGPR/lane | Waves/SIMD | Waves/WGP | 256-thr WGs/WGP (8 waves) |
|---|---|---|---|
| 64 | 16 | 64 | 8 (LDS will cap first) |
| 128 | 8 | 32 | 4 |
| 256 | 4 | 16 | 2 |

SGPRs do not limit occupancy on GFX10+ (LLVM + GPUOpen). LDS 64 KB/WG, 128 KB/WGP. Two WGs/WGP ⇒ each WG ≤ 32 KB after 1 KB rounding.

`llvm-calc-occupancy -mcpu=gfx1030 --wg-size=256 --vgprs=N --lds=K` before arguing.

### 5.2 Decode `M=1,2,4` — skinny, not tiled

**Do not** launch a 64×64 WMMA-shaped tile. Follow the scalar RDNA3 geometry, fp16 only:

| Knob | Value | Source |
|---|---|---|
| `THREADS_X` / `BLOCK_KN_SIZE` | **256** | `q_gemm_rdna3.cu`; 512 was measured worse for fp16 decode |
| N per thread | **4** | `n = offset_n + t*4`; N must be `% 8 == 0` (64-bit CAS) |
| `M_COUNT` | 1 / 2 / 4 for M=1 / ≤3 / ≤7 | same file |
| Grid | `(ceil(N/1024), ceil(M/M_COUNT), ceil(K/256))` | `BLOCK_KN*4 = 1024` N-cols/block |
| LDS A | `M_COUNT × (256+8) × 2 B` = **528 / 1056 / 2112 B** | `LDS_PAD=8` |
| C in VGPR | `M_COUNT × 4` fp32 = 4 / 8 / 16 | plus ~8–24 for addresses / `half2 dq` (range, not measured) |
| Target VGPR | **≤ 64** (16 waves/SIMD) | occupancy table |
| A staging | LDS for fp16 even at M=1 (`USE_LDS_A` is true for `half`) | file: bf16 M=1 skips LDS; you have no bf16 |
| K*M LDS cap if you take the hybrid skinny shape | **32768** fp16 elems (64 KB) | `LDS_CAPACITY_ELEMENTS` in `rdna_hybrid_w4a16.py` |

Skinny `wvSplitK_int4_g` geometry (gfx11/12; **rewrite** for gfx1030):

| Knob | Value | Source |
|---|---|---|
| Block | `(THRDS=32, 16)` = **16 waves**, 512 threads | `WVSPLITK_INT4G_LAUNCH` |
| `A_CHUNK` | 16 | template |
| `YTILE` / `UNRL` | 1–4 / 1–4 from `N_in` and `sYT` | `WVSPLIT_INT4G_TILE` |
| `N_in` (batch) | 1..5 | `MAX_SKINNY_BATCH_SIZE = 5` |
| Grid | `CuCount` (one block per CU, persistent over N) | `dim3 grid(CuCount)` |
| Reduce | DPP `row_shr` + `__shfl_xor(16)` wave32 | `REDUCE_SUM_DPP_WAVE32` — **this DPP sequence is written for gfx11**; verify DPP encodings on gfx1030 before copying |
| LDS | whole A, `64 KB / 2` as `half` capacity | `#define LDS_SIZE 64*1024` |

On a 72-CU V620, persistent `grid=CuCount` is the right skinny idea (same as gfx1100’s 96-CU launch). The **empty `__HIP__GFX1X__` stub** means you cannot call the vLLM symbol and expect work.

**Recommended decode seed (compile-and-measure, not a claimed peak):**

```
wave32, WGP, WG=256
M_COUNT = M          # 1, 2, or 4
BLOCK_KN = 256
N_tile   = 1024      # 256 threads × 4 cols
LDS      = M_COUNT × 264 × 2 B
VGPR cap = 64
opcode   = __builtin_amdgcn_fdot2
A in LDS, B streamed as int4×4 (int4 vector = 16 B = 32 nibbles = 32 K)
software-pipeline 4 weight loads (the file already does this)
```

If `K=4096, M=1` and you only launch `ceil(N/1024)*16` blocks, that is `N/1024*16` wavefront-blocks. For `N=4096` → 64 blocks. 72 CUs ⇒ some CUs idle. That is the 256-vs-512 lesson inverted: **too few blocks**. Prefer `BLOCK_KN=256` (more `gridDim.z`) over 512.

### 5.3 Prefill `M≥32` — tiled DOT2, not WMMA

vLLM’s fat path is WMMA. Yours cannot be. Two legal starting points, both sourced as *seeds*:

**A. VALU GEMM recipes** (`rdna2-lds-tiles.md` §recipes 1–2), applied to W4A16 by keeping A fp16 and treating B as packed (LDS bytes for B ÷ 4 if you store packed, or same as fp16 if you dequant into LDS):

| # | BM × BN × BK | WG | LDS if both tiles fp16 | 2 WG/WGP | C fp32/thread |
|---|---|---|---|---|---|
| 1 | **64 × 64 × 32** | 256 | 8 KB | yes (double 16 KB) | 16 |
| 2 | **128 × 64 × 32** | 256 | 12 KB | yes (double 24 KB) | 32 |
| 3 | 128 × 128 × 32 | 256 | 16 KB | tight with pad+double | 64 → you are in the 128-VGPR / 8-wave regime |

Inner loop: load A (`half2`) + dequant 8 B-nibbles → 4× `fdot2` per output. Unroll K by 16 or 32 to cover the **5-cycle VALU dest latency** (RDNA architecture deck).

**B. Triton table that PR #52391 will select on gfx1030** (`triton_w4a16.py`, gfx1151 numbers, **not** measured on V620):

| M | BLOCK_M, BLOCK_N, BLOCK_K |
|---|---|
| ≤ 32 | 32, 32, 64 |
| ≤ 64 | 64, 64, 32 |
| else | 128, 32, 64 |

Then `BLOCK_K = min(BLOCK_K, group_size)` (PR #39705: `BLOCK_K > gs` silently applies the wrong scale). Hybrid’s gfx1151 table is richer (per-shape overrides, `num_warps`); gfx1030 is **not** in that table. PR #52391’s own V620 bench (open PR body):

| Model | Kernel | c=1 | c=8 | c=32 |
|---|---|---:|---:|---:|
| Qwen2.5-7B-GPTQ | Triton W4A16 | 8.01 | 39.68 | — |
| Qwen2.5-7B-GPTQ | Exllama | 10.23 | 51.51 | — |
| Qwen3.6-27B-GPTQ-W4A16-G32 | Triton W4A16 | 6.44 | 15.83 | 26.74 |
| Qwen3.6-27B-GPTQ-W4A16-G32 | Exllama | 18.49 | 21.15 | 46.42 |

So on this user’s hardware, **stock Triton W4A16 loses to ExLlama at decode**. A custom DOT2 decode kernel is the first win; a custom tiled prefill kernel is the second. Do not ship the gfx1151 tile table as “gfx1030-tuned.”

**Skinny vs tiled, one sentence:** `M≤4` and `K·M` fits 64 KB → skinny (A in LDS, persistent CU grid, no B tile). `M≥32` → 2-D tiled DOT2 with A and (packed or dequant) B in LDS. `5<M<32` is the messy band: RDNA3 uses scalar `M_COUNT=8` or WMMA 16×16; on gfx1030 start with `M_COUNT=8` scalar and only write a 32×32 tile if that saturates badly.

### 5.4 VGPR guess for the decode kernel (labelled as such)

Not a measured RGA dump. Arithmetic from the source:

- `block_c[M_COUNT][4]` fp32 → 4 / 8 / 16 VGPR
- `half2 dq[4][4]` live during the j-loop → 16 VGPR (or recycled)
- `int4 b_w[4]` prefetch → 16 VGPR
- pointers / `k` / group state → ~8

Total in the **40–64** band is plausible at `M_COUNT≤4` if you `#pragma unroll 1` the column loop the way the bf16 path does. Crossing 64 VGPR drops you from 16 to 8 waves/SIMD. **Measure.**

## 6. MoE — `moe_gptq_gemm_rdna3`

### 6.1 What the fused kernel actually does

File: `csrc/rocm/moe_q_gemm_rdna3.cu`. Python: `compressed_tensors_moe_wna16_rdna3.py`.

One launch per GEMM (w1, then w2). **No WMMA.** Same dequant + `fdot2` + 64-bit CAS as the dense scalar kernel, plus:

```
token_block = blockIdx.x
expert_id   = expert_ids[token_block]          // -1 → return
A row       = sorted_token_ids[base + m] / top_k
B           = b_q_weight[expert_id]            // [E, K/8, N]
```

Grid: `(num_token_blocks, ceil(N/1024), ceil(K/256))`, block 256.

`BLOCK_SIZE_M ∈ {1,2,4,8}` (C++ switch). Python picks **1 if `num_tokens≤4` else 4**.

w1: `a [M,K] → c [M·top_k, N_gate]` (pre-zeroed). Optional `topk_weights[token_id]` multiply.

w2: `output_topk = top_k` so `out_row = token_id / output_topk` — several experts CAS into the same hidden row. That **is** `moe_sum`. Saves a kernel and the `w2_out` buffer.

Weights: `ops.gptq_shuffle` per expert; zeros synthesized as `uint4b8.bias-1=7` packed `[E, groups, N/8]`. **`zero_offset` hardcoded to 1** (GPTQv1 only).

LDS: only A, `BLOCK_SIZE_M × (256+8) × 2 B` = 528 B (M=1) … 4.2 KB (M=8). **No expert-weight tile in LDS.** B is streamed. “LDS for expert tiles” in the question is **not** what this kernel does.

bf16 `BLOCK_SIZE_M==1` skips LDS and reads A from global (same InstCombine-opacity trick). **Drop that branch.**

### 6.2 What breaks without WMMA

**Nothing in this file.** It never called WMMA. Prefill MoE at large token counts stays on `BLOCK_SIZE_M=4` or 8 DOT2; that is already the gfx1100 design. The thing that breaks on gfx1030 today is the **build gate**, not the ISA:

- CMake: `.cu` only if `VLLM_GPU_ARCHES MATCHES "gfx1100"`
- `torch_bindings.cpp`: `#ifdef VLLM_ROCM_GFX1100`
- Device: `#if defined(__HIPCC__) && defined(__gfx1100__)`
- Python: `hasattr(torch.ops._rocm_C, "moe_gptq_gemm_rdna3")` then `_try_get_rocm_moe_method()`

A gfx1030 port is: compile the **scalar** MoE TU with `__gfx1030__`, delete bf16, keep fp16 `fdot2`, keep CAS, keep `output_topk`. Do **not** add a WMMA MoE “to match dense prefill.”

### 6.3 Routing cost

`moe_align_block_size` still runs on host/device before the GEMM (Python). The HIP kernel does not sort. Padding waste at `BLOCK_SIZE_M=8` on decode is why they force `BLOCK_SIZE_M=1` for `num_tokens≤4` (“eliminates ~75% of padding waste”, PR #44075).

## 7. Known pitfalls

### 7.1 Occupancy 0 (llama.cpp, gfx1030/1031)

https://github.com/ggml-org/llama.cpp/issues/24672 and https://github.com/ggml-org/llama.cpp/discussions/23310

| Config | Threads | VGPR | LDS | Compiler occ. | `cudaOccupancyMaxActiveBlocksPerMultiprocessor` |
|---|---|---|---|---|---|
| decode `<256,256,1,8>` | 128 | 102 | 21 504 B | 6 waves/SIMD | **2** (runs) |
| prefill `<256,256,4,8>` | 256 | 203 | 37 888 B | 4 waves/SIMD | **0** (assert) |

Compiler occupancy is not launchable occupancy. A 256-thread / ~200 VGPR kernel can be unloadable on gfx1030 even when LDS is 38 KB (well under the 64 KB workgroup cap). Stay at 128 threads or at most 128 VGPR until a runtime occupancy query returns at least 1.

### 7.2 Bank conflicts on packed int4

- Sequential `int` / `half2` along K, wave32, WGP: `bank = (addr/4)%64` → 32 distinct banks, **conflict-free** (LDS brief §1.5).
- `half` scalar walk: 2-way (never do this).
- Column walk of a tile whose leading dwords `% 64 == 0`: 32-way disaster. Packed int4 stored as `uint32 [K/8, N]` with `b_ptr += size_n` per K-step: if you then **read a column of A from LDS** at stride `BLOCK_KN` dwords, that is the GEMM-A column problem. RDNA3’s `LDS_PAD=8` makes the A row stride 264 half = 132 dwords. File comment claims `(m*132)%32 = (m*4)%32`. On **64-bank WGP** it is `(m*132)%64 = (m*4)%64`. Still unique for `m<16`. Do not delete the pad.
- XOR/swizzle is still legal (CK formula in the LDS brief). Not used in `q_gemm_rdna3.cu`.
- Dequant LUT in **scalar/constant cache**, indexed by nibble per lane: llama.cpp #24438 (gfx1151, but the mechanism is RDNA-family K$): “per-lane nibble index into a dequant LUT serialized the whole inner loop 32-ways.” The bit-trick exists so you **never** do that. Do not “simplify” dequant to a 16-entry table in `__constant__`.

## AWQ prefill scalar fp16 atomic (dest `7779514b`)

`q_gemm_rdna2_common.cuh` adds `atomic_add_f16(half*, half)` — CAS-loop on `unsigned short` via `atomicCAS`. HIP on gfx1030 does **not** expose `atomicAdd(__half*, __half)`.
