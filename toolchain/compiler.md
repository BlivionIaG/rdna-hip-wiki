## Gotcha — HIP `__shfl_xor` keeps a bounds check in full-wave reductions (2026-10-07)

CLR's `__shfl_xor` (`amd_warp_functions.h`) has a lane bounds check that should fold away when `width == warpSize`, but LLVM can't prove `__lane_id() < warpSize`, so it survives as `v_cndmask` in every butterfly step. [rocm-systems#11618](https://github.com/ROCm/rocm-systems/pull/11618) (open since 2026-09-15) masks the lane id with `warpSize - 1`; on a 5-step wave32 sum it cuts VALU from 32 to 11 and `v_cndmask` from 5 to 0 on **gfx1030** and **gfx1100** (wave64 gfx90a: 40 → 17). Until it lands in a pin we build with, grep hot reductions for `v_cndmask` with `--save-temps`; a local helper that does `__builtin_amdgcn_ds_bpermute(((__lane_id() & (warpSize - 1)) ^ mask) << 2, v)` gets the same code. Narrow `width` (e.g. 8) is unaffected either way. Craft note only; no pin or dest change.

## Gotcha — full `#pragma unroll` spills VGPRs on RDNA, and upstream CI won't catch it (2026-10-06)

llama.cpp [#29910](https://github.com/ggml-org/llama.cpp/pull/29910) (open) shows the Q2_K MMQ kernel spilling heavily on every AMD target because of full `#pragma unroll` over the `j0` loop plus a staged `y_df[]` temp array. Going to `#pragma unroll 2` (and `unroll 1` on one inner loop) and reading the scale inline took the reported spill counts from 836 to 0 on **gfx1030** (DP4A path) and from 1387 to 0 on **gfx1100** (MMA path); gfx906 pp2048 at ub 512 went 205 → 571 t/s. The lesson for our TUs: unroll factor is a register-pressure knob, so sweep `1/2/4` and read `-Rpass-analysis=kernel-resource-usage` (`VGPRs Spill:` / `ScratchSize`) per arch instead of defaulting to full unroll. llama.cpp's own spill gate ([hip-quality-check.yml](https://github.com/ggml-org/llama.cpp/blob/master/.github/workflows/hip-quality-check.yml) + `scripts/hip/gcn-cdna-vgpr-check.py`) builds **gfx908 only**, so RDNA spills pass upstream CI. The script just parses the remarks log, so the same gate can be pointed at `gfx1030;gfx1100;gfx900` in a fork. Craft note only; no pin or dest change.

## Gotcha — HIP `__byte_perm` is not `v_perm_b32` (2026-10-05)

In HIP (`clr/hipamd/include/hip/amd_detail/amd_device_functions.h`), `__byte_perm(x, y, s)` is a C emulation that indexes a byte array four times. It is not a single instruction, and with a runtime selector it can be very slow. For hot unpack paths, use `__builtin_amdgcn_perm(hi, lo, sel)` → `v_perm_b32`. It exists on gfx900, gfx1030 and gfx1100. The semantics differ, so remap rather than rename: operand order is swapped (`lo` = bytes 0–3), the selector is one **byte** per output byte (not a nibble), and selector 12 gives `0x00` and ≥13 gives `0xFF`. Evidence: llama.cpp [#29927](https://github.com/ggml-org/llama.cpp/pull/29927) (open), Q1_0 unpack, gfx906 tg128 67 → 129 t/s. Check the ISA with `--save-temps` and test against the CUDA reference. Craft note only; no pin or dest change.

## 2026-09-03 — wave64 follow-ups (still not a dest lever)

Two more data points on the same thread, both open:

- [rocm-systems#9647](https://github.com/ROCm/rocm-systems/pull/9647) (`jmmartinez`, updated 2026-09-03) **removes a CLR hack that forced wavefront size 64** when the running executable's name matched Geekbench 5 (`geekbench_x86_64.exe`). Details worth knowing: the hack was **Windows-only, never on Linux**, and it missed the GUI's own `geekbench_avx2.exe`, so AMD's internal numbers were not reproducible by hand (ROCM-24860). Takeaway for us: a *runtime-side* wave-size override has existed in CLR, keyed on process name — so on Windows, wave size is not purely a compile-time property. On Linux/gfx1030 there is no such lever; our wave32 dest is unaffected.
- [ROCm/llvm-project#4213](https://github.com/ROCm/llvm-project/issues/4213) is the Comgr **hotswap** tracker, and it grew a concrete checklist: int VOP1/2/3 arithmetic and VOPD dual-issue ([#4234](https://github.com/ROCm/llvm-project/pull/4234)), int VOP bit ops ([#4251](https://github.com/ROCm/llvm-project/pull/4251)), SOPC compare, SOP2 scalar shifts, wider SMEM (`s_load_b96`), SOPP control flow ([#4079](https://github.com/ROCm/llvm-project/pull/4079)), EXEC-mask handling ([#4081](https://github.com/ROCm/llvm-project/pull/4081)), and `waitcnt` ([#4077](https://github.com/ROCm/llvm-project/pull/4077)). [#4267](https://github.com/ROCm/llvm-project/pull/4267) (source wave size; closed unmerged) was part of the same series. Note **VOPD is gfx11+**, so that piece is a gfx1100 concern, not gfx1030 (GFX10.3 has no dual-issue VOPD).

Neither changes the pin. Keep watching #4213 as the place where hotswap coverage per ISA family is tracked.
